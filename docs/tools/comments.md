# Comments and highlights

Open a PDF and choose **Comment** from All tools or the quick toolbar. Click a bare part of the page to place one sticky note, type its text, then choose **Save comment**. The PDF renders the note icon; the transparent on-page target opens the editor without drawing a second icon.

Choose **Add area highlight** and drag one rectangle on the current displayed page. It highlights an area, including scans; it does not select or infer text. The PDF renders a fixed translucent yellow appearance. The UI does not draw a second saved fill. A highlight's optional description can be empty; the native layer normalizes whitespace-only descriptions to none and preserves nonblank Unicode text and its surrounding whitespace. The rectangle cannot be resized after creation. Keyboard drawing is not implemented. Escape, a lost pointer, a page move, zoom, or a revision change cancels an unfinished drag.

To highlight text, choose **Select**, select supported embedded text on one visible page, then choose **Highlight selected text**. The browser selection must remain in one current, mounted text layer. Its endpoints map outward to complete `page_text_geometry.characters` entries, so a partial Unicode glyph is never saved. Native code derives the saved glyph quads in its own geometry-array order; it does not use browser rectangles or promise visual paragraph order. Cross-page, mixed-layer, disconnected, collapsed, stale, unsupported, or truncated selections do nothing. This slice has no keyboard-only way to draw an area highlight, but normal keyboard text selection can create a text highlight.

Use the **Comments** rail button to list every note and highlight. Select an item to edit or delete it. An annotation fully hidden by the current crop has no on-page target, but remains in the list with an explicit hidden status and can still be edited or deleted. Comment mode enables keyboard-focusable transparent edit targets. Area-highlight placement, Select, and Pan leave those targets inactive, so an existing large highlight does not block an overlapping drag, text selection, or panning. Press **Escape**, choose Select, or press **H** to leave placement mode. While an annotation is saving, closing the editor, tab, or workspace is blocked.

Annotations have no author field yet; no name is written into the file. Each note and highlight records when it was created and last changed, in UTC, and a subject ("Sticky Note" or "Highlight"), as Acrobat does. Each sticky note is saved with a closed popup at the right edge of the page, where Acrobat and other readers show its text. Notes saved by earlier versions gain one when their page is saved again. Unsaved comment edits recovered after a crash are stored in a newer recovery format that 0.3.1 and earlier cannot read; those versions then refuse to open the affected PDF. Before installing an older version, open each PDF that offers recovered edits, save any you need to a copy, and choose Open original when it is offered again, so that no recovery record remains. A note must contain nonblank, NUL-free text. A highlight description is optional. Each body may use at most 8 KiB of UTF-8; a document may have at most 1,000 notes and highlights combined and 1 MiB of text combined. Current page crop and rotation are handled by the native layer: notes and area highlights use normalized displayed positions, while text highlights use geometry-array indices.

A text highlight may paint at most 256 positioned glyph quads. Notes and area highlights consume one geometry slot each; the document has 4,096 slots total. Whitespace without bounds can remain part of a selected logical range but has no painted quad. If a visible page would need more than 512 transparent edit targets, it shows a route to the Comments list instead; native paint and every list entry remain available. Text geometry remains all-or-nothing: the pinned engine's astral-character mapping fixture is explicitly unsupported, while Unicode annotation bodies are retained.

Supported notes and highlights follow page rotation, crop, move, delete, extract, and split operations. They participate in undo/redo, Save a Copy, reopening, visible rendering, and immutable print snapshots. Printed pages render their native appearance only; bodies do not enter Page text or Find.

PDFs with annotations from other apps (or links) can be commented on. Your own notes and highlights are added alongside theirs. The other annotations are shown as the PDF draws them and listed in the Comments panel as view only, with type, page, author, date and plain text. Popups, reply status, links and form fields are not listed. A saved copy keeps their objects and content unchanged, in their original order on the page. The copy is written anew, so the bytes are re-serialised: real numbers are stored at single precision. A page whose comments you did not change is not rewritten. One of this app's own notes is also kept as view only when it was changed outside the app, or when another annotation refers to it, such as a reply made in another app. Rich formatting, actions, attachments and media are neither shown nor run. Deleting, extracting or splitting pages of a file with other apps' annotations or links is still refused; rotating, cropping and moving pages keep them.

Commenting is unavailable for signed, encrypted, form, tagged, page-label, or article-thread documents, and for a malformed annotation array. This refusal leaves the source unchanged, and the annotations are still listed as view only. Combine Files, Insert Pages, and Replace Pages refuse annotated source documents. Editing or deleting other apps' annotations, replies and author identity are not implemented yet.

Highlights are saved with each quadrilateral's corners in the order Acrobat writes and PDFium reads (top-left, top-right, bottom-left, bottom-right). Up to 0.3.1 the app wrote a different order. Those files carry their own appearance and still open, but a reader that rebuilds the appearance draws such a highlight blank. To rewrite them in the new order, change any comment in the file and save a copy.

Verification includes 144 frontend/release tests and 108 native tests with one ignored manual probe; the production frontend and standalone Windows debug builds passed. The native focused text-highlight gate passed 9 tests. Native regressions cover cardinal rotations, inherited and offset crops, Unicode bodies, source-text mapping support/refusal, history limits, reopening, note and highlight pixels, immutable print snapshots, supported page operations, and refusal cases. Focused UI tests and a mocked browser harness cover note placement, area dragging, actual DOM multiline and keyboard selection, whole-glyph Unicode mapping, cross-layer and stale disposal, transparent hit geometry, the 512/513 target fallback, hidden annotation editing, stale requests, UTF-8 limits, pointer cancellation, mode behavior, and busy/Escape handling. Desktop save-dialog and saved-output interaction, actual printer output, and installed-app checks remain separate evidence.
