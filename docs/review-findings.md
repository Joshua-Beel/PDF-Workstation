# Development review

This review covers the current frontend, native worker, page editor, IPC, update dialog and release scripts. It is an incremental review of the source build, not completion of the requested final review or certification of the published installer.

## Open risks and verification work

- Forms hardening was re-run with large generated fixtures. The earlier audit never recorded its hypotheses, so the source tests now cover the shapes its scope implies, built with lopdf and run through `FormDocument::parse`/`prepare`, plus one 256-field, 16-page copy through the worker's `FillFormCopy` with PDFium validation. Two defects reproduced and are fixed. First, a filled copy kept the replaced appearance of a changed or cleared text or choice field, and objects from superseded incremental revisions, as unreferenced objects, so a cleared value stayed recoverable from the copy. Copies now keep only objects reachable from the trailer. Second, the lenient loader with its 1 MiB per-stream limit silently dropped an oversized object stream or a malformed object, which the copy would then have omitted. A form whose cross-reference entries did not all load is now refused as a whole. The following did not reproduce and are now regression tests that assert whole-form refusal or correct output: more than 256 fields or widgets on any page layout, 4,097 pages, widgets shared between pages or fields, widgets without `/P` or on pages outside the tree, non-widget annotations, 2,000-level and cyclic `/Kids`/`/Parent` trees, inherited `/FT`, `/T` and `/DA` (only AcroForm-level `/DA` is supported, and it fills correctly), reference cycles, 100,000-entry `/Opt` arrays, 1 MiB values and names, malformed, bomb and unsupported-filter appearances, duplicate names across encodings and field kinds, `/NeedAppearances`, RC4 encryption, and object- and xref-stream sources (which fill correctly). In a debug test build, parse plus prepare took about 0.8–1.1 ms per field up to 256 fields and about 0.17 ms per page up to 4,096 pages, which is linear. The forms 50,000-object limit is still checked after its own load, but that load now only re-reads a source that already passed the open-time load limits below. Installed-app behavior remains unverified.
- Open-time lopdf load limits (source tests and debug-build measurements; installed-app behavior not exercised). Every open (plain, password, recovery restore) loads the source through `pdf_load::load` before PDFium: more than 1,000,000 indirect-object headers are refused before lopdf parses anything, any stream decoded during the load stops at 32 MiB, object streams are measured before lopdf decodes them against a 256 MiB total and the object limit, and an object stream whose entries overlap is refused. Each refusal ends "Nothing was opened.". Structural export and Combine prune unreachable objects in linear time instead of lopdf's quadratic `prune_objects`. Still open: lopdf's encrypted-document loader ignores the load filter, so for an encrypted file (including one with an empty user password) only the object-header count and the 32 MiB per-stream cap apply, with no total and no overlap check; cross-reference entries that share one offset make lopdf parse that object once per entry; a dense direct array costs much more memory than its file bytes. PDFium showed no cap at that size: a catalog inside an object stream that inflates to 1 GiB opened in PDFium alone at a 2.1 GiB peak working set; the lopdf check now refuses that file before PDFium sees it. Content streams are decoded only at render time and are not covered.
- Cross-reference resolution (source tests; real work PDFs measured read-only; installed app not exercised). Every `pdf_load::load` now re-walks the cross-reference chain (`xref_resolve.rs`) and makes lopdf's objects agree with it: object-stream members with a free or missing entry are removed, unreachable objects the readers disagree about are removed, and a file where the standard, lopdf and the bundled PDFium disagree about a reachable object is refused for editing (viewing works). Remaining: PDFium's own deviations (it ignores a `/XRefStm` whose section has no `/Prev`, keeps objects a newer revision freed) are measured on generated files only; files lopdf rebuilt by scanning, and files without object streams whose chain this walk cannot read, keep lopdf's load unchanged.
- File reads and PDFium's source copy have no total memory limit. The worker queue admits at most 256 pending non-render requests (cleanup is never refused) beside the 32-key viewer-render limit. Undo/redo snapshot allocations now share a 32 MiB per-document budget with oldest-history eviction. Close and EndPrint can bypass a bounded head run of viewer renders, but broader rapid-scroll and memory-pressure limits still need measurement.
- Matching page counts do not prove that two parsers repair a damaged page tree in the same order. More damaged-document fixtures are needed.
- Native parser crash isolation, fuzzing, a real-document compatibility corpus and sustained memory-pressure tests remain missing.
- Reply leases stop when a public service method accepts and returns a plain DTO. They do not establish that Tauri, WebView, or JavaScript received that result; post-acceptance transport loss remains unverified.
